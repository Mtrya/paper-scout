**Abstract** Foundation models are becoming remarkably reliable at high-level reasoning, yet they remain too slow and costly to serve as fine-grained controllers. Conversely, fast policies like VLAs and whole-body controllers offer more efficient reflexes, but struggle to generalize. While pairing a deliberative brain (foundation models) with a reactive cerebellum (fast policies) seems natural for embodied systems, two obstacles remain: methods are built and scored on incompatible stacks, and their asynchronous coordination is difficult. For example, an agent that calls the VLA in the agentic loop can stall the fast execution, while a VLA that calls the agent on errors tends to re-trigger fallbacks repeatedly or completely miss silent failures. To address this, we propose REA (Routed Embodied Agent), a unified runtime where a deliberative System 2, an embodied router System 1 and reactive System 0 policies cooperate under a single golden rule: no running policy waits on the brain. Instead of querying the brain at each failure, REA employs a route memory that stores each policy’s measured success ahead of time, a boundary-triggered judge gate that consults the brain on policy execution, and a shared-budget escalation ladder for bounded recovery. Evaluated on 3,000 test episodes across 60 LIBERO-Pro tasks, REA reaches 95.9% success and beats the best single-agent baseline in its own policy pool (94.7%) while reducing control steps by 25% and control time by 17%. In a separate 100-episode RoboTwin 2.0 study, REA achieves 84% success with VLA policies and 86% with VLA+code, compared with 80% for the strongest single VLA baseline MEDex. These results demonstrate learned and programmatic policies operating within the same runtime. REA also transfers to BEHAVIOR-1K and a real Unitree G1 humanoid, achieving the highest observed success among the compared methods.

## 1. Introduction

Foundation-model agents have become capable embodied brains: a coding agent can write a manipulation program that calls segmentation, grasp planning and inverse kinematics [1, 2], and a language or vision–language model can decompose a command [3–5] or tell whether a task succeeded [5, 6]. These abilities are expensive: in our runs ASPIRE’s repair loop [2] spent a median of 43 min per LIBERO task, and a Codex + GPT-6 pipeline consumed 89M input tokens to generate programs for 60 LIBERO-Pro tasks. Nor can the brain simply act as the controller: in our probes, models emitting one-token or Cartesian IK actions solved 1 of 1,987 and 0 of 600 LIBERO-Pro episodes (Appendix C.4, Figure 6). Vision–language–action models (VLAs) [7–10] and whole-body controllers such as SONIC [11] act at a few to tens of hertz, far faster than an agent deliberates, but VLAs that exceed 90% on LIBERO collapse under LIBERO-Pro’s perturbed test set [12].

Embodied intelligence should therefore separate a deliberative brain from a reactive cerebellum, as recent dual-system robot models do [13–17]. However, two obstacles still stand in the way. First, **there is no common runtime for comparing agents and VLAs**: agent- and VLA-based systems are each built on their own simulator, robot, observation format and success criterion, so it is hard for them to test on the same episodes. Second, **asynchronous coordination is hard** (Figure 3). When the agent drives and calls the fast policy, the fast loop waits on every agent decision: an agent advisor that the router waits for leaves the robot idle for 2.6s per LIBERO-Pro episode, 20% of its control time (Figure 4). When the fast policy drives and calls the agent on errors, a persistent error re-triggers the brain at every recurrence, while most failures raise no error at all: an exception-triggered router escalated only 6 times in 590 LIBERO-Pro episodes although 166 failed. Re-execution is not always reliable either: if the task has already succeeded, running it again may undo the result.

We address the above issues with REA, a Routed Embodied Agent runtime (Figure 1) designed to unify agent and VLA runtime across simulators and real robots. REA implements a three-level system: **System 2, the brain**, is an agent that generates policies offline or online, and provides advises or judges; **System 1, the embodied router**, decides which policy to run and when to consult the brain without blocking a running policy; **System 0, the cerebellum**, holds fast policies (frozen programs, VLA policies or whole-body controllers) that return control to the router at segment or policy boundaries. REA also provides a unified evaluation framework for any policies including code-as-policies and VLAs. Figure 2 shows REA across simulators and on a real robot.

Our central idea is to let the brain prepare policies offline and intervene online only when there is a need, so that no running policy has to wait for it. Besides the conventional serial execution mode, our REA also offers asynchronous mode: policies run at their own rate, with System 2 running in parallel to provide advice or judge. Our proposed method achieves this via three designs. **To keep the brain off the dispatch path**, REA contains a **route memory** of each policy’s per-task success and cost on development episodes, so choosing a policy can be isolated from the System 2’s reasoning process and call System 2 on dilemma. **To catch silent failures without re-firing on errors**, a **boundary-triggered judge gate** consults System 2 concurrently and decides whether a task is finished: if not done then escalates, if done then stops and protects completed work. **To keep recovery bounded**, an **escalation ladder** dispatches the next policy from the current state under one shared step and time budget.

## 2. Related Work

**Embodied brains and fast policies.** Large models serve as the deliberative layer of robot systems: SayCan [3] grounds LLM plans in learned affordances, PaLM-E [5] embeds observations into a language model, and Inner Monologue [4] and SayPlan [18] re-plan from feedback. Code-as-policy methods let the agent write the controller: Code as Policies [1] and ProgPrompt [19] compose perception and motion primitives, Voyager [20] iterates on executable policy code with environment feedback (Eureka [21] does so for reward code), and ASPIRE [2] scales repair and evolutionary search to LIBERO; more generally, ReAct [22] interleaves reasoning with actions and Reflexion [23] adds self-reflection across trials. At the other end, vision–language–action models such as RT-2 [7], OpenVLA [8], Octo [9] and 𝜋<sub>0</sub> [10] act far faster than an agent deliberates but generalise within their training distribution [12], and whole-body controllers such as SONIC [11] track motions commanded from above. REA keeps the agent as System 2, off the control loop and the dispatch path, and lets any fast policy serve as System 0.

**Dual-system control.** Following Kahneman [24], GR00T N1 [13] and Helix [14] train a slow VLM with a fast action head that run at fixed, different rates, and Helix 02 [15] adds a learned 1 kHz whole-body “System 0”; Hi Robot [16] and Gemini Robotics 1.5 [17] let a VLM planner command a VLA, and real-time chunking [25] overlaps a VLA’s inference with its execution. Every level there is a learned model of one stack. REA keeps the level names but not their semantics: System 1 is a router that emits no actions, any policy can serve as System 0, and System 2 is an independently developed agent that no running policy waits for.

## 3. The REA Runtime

REA answers one question: how can a slow, general brain and fast, narrow policies cooperate without the brain ever blocking a running policy?

**REA variants.** REA denotes the shared runtime. Its three variants in experiments differ in policy selection and recovery, see details in Algorithm 1 and Appendix B.1:

• **REA-M (route memory).** Uses route memory to select policies and the exception gate to trigger recovery after an exception or truncation, with no online System 2 calls.

• **REA-A (agent routing).** Calls a System 2 agent to select the initial policy and choose a recovery policy whenever the exception gate triggers.

• **REA-V (visual judging).** Uses route memory to select policies and a visual judge at policy returns to decide whether to stop (done) or advance along the escalation ladder (not\_done).

## 3.1. Three-Level Contract

An episode is a task 𝑡 with instruction ℓ<sub>𝑡</sub>, an initial state indexed by seed 𝑠, a step horizon 𝐻 and a wall-clock budget 𝑊.

**System 0: policy execution.** A policy 𝑝 is any controller that can start from the current state and eventually returns, $( \Delta , \delta , e , \tau ) \gets \mathrm { R U N } ( p ;   H - u ,   W - w )$ , where 𝑢, 𝑤 are the steps and seconds already spent, Δ, 𝛿 those of this run, 𝑒 an exception or ⊥ and 𝜏 a truncation flag. A policy may also yield at segment boundaries and be resumed: a VLA action chunk, a motion interval, or a program that pauses every 100 control steps with its stack preserved. Policies run their own closed loop at native rate. On LIBERO-Pro they are frozen Python programs written by coding agents; they call SAM 3 [35], ContactGraspNet [36], PyRoki inverse kinematics [37] and blocking motion primitives inside a sandbox that rejects identifiers (such as getattr) that could reach simulator state. On RoboTwin 2.0, the VLA extension also executes learned action-chunk policies and an online code policy through this interface (Section 4.6).

**System 2: the brain, offline and online.** Offline, Generate(𝑡) produces candidate policies $\mathcal { P } _ { t }$ (the “Frozen programs” box of Figure 1). Online, the brain offers two services: Judge $( f _ { 0 } , f _ { k } , \ell _ { t } )$ ∈ {done, not\_done} compares the episode-initial and current frames with the instruction, and Advise(𝑜) recommends a candidate from text inputs (used by REA-A at dispatch and by the blocking advisor baseline). For REA-A, the inputs are the route memory, candidate source code, proprioception and exception history.

**Backends** implement Reset, Render, the policy API and a Score read once after the last run: LIBERO/LIBERO-Pro on MuJoCo/robosuite [38–40], BEHAVIOR-1K on OmniGibson/Isaac Sim [41], RoboTwin 2.0 on SAPIEN [42] and a Unitree G1, where Score is the operator’s judgement.

The router owns every control-flow decision, with one module per coordination problem.

**Route memory: dispatch without the brain.** Before evaluation, the router runs each candidate $p \in \mathcal { P } _ { t }$ on $n _ { p }$ development episodes (seeds disjoint from test seeds, seeded-random resets) and stores the success rate $\hat { r } _ { t , p }$ and mean steps $\hat { c } _ { t , p }$ . The first policy is arg max ${ } _ { p }   \hat { r } _ { t , p } ,$ ties broken by lower $\hat { c } _ { t , p } \colon$ at test time dispatch is a lookup (the route table of Figure 1).

**Boundary-triggered judge gate: consult the brain when a policy returns.** Most failures are silent: Run returns $e = \bot$ with the task unfinished, so an exception trigger never fires. REA-V therefore calls Judge once per policy return; done ends the episode and protects completed work, not\_done escalates. A free exception gate escalates only on an exception or truncation and never calls System 2.

**Escalation ladder with a shared budget.** The ladder $L _ { t }   =   [ \mathrm { \bf f i r s t } ( t )$ , other(𝑡), first(𝑡)] (with three candidates, all three in route-memory order; one rung with one) launches each escalation from the current state, and every run and brain call draws on the same $\left( H - u , W - w \right)$ , so an episode never exceeds a single-policy budget.

**Baselines.** A single-policy baseline is Algorithm 1 with $K { = } 0 ;$ blind retry uses the unconditional gate always.

**Learned dispatch for VLA and code policies.** The same System 1 interface also supports an observation-conditioned selector. In the RoboTwin VLA study, an encoder maps the initial instruction, images and robot state to $h _ { 0 _ { 1 } }$ , and a success head scores each candidate as $q _ { p } = \sigma ( w _ { p } ^ { \top } h _ { 0 } + b _ { p } )$ . The router selects $p ^ { * } = \arg \operatorname* { m a x } _ { p } q _ { p }$ before execution and keeps that policy for the episode. Adding a codepolicy head extends the seven-VLA selector to a mixed pool without changing the policy execution interface (Section 4.6).

## 3.3. Aligned Evaluation Protocol

Within each matched LIBERO-Pro comparison, methods use the same (task, seed) pairs, initial-state semantics, horizon and wall budget, the same frozen policy code wherever they share a library, and one final Score. Within a campaign on one host, each episode key keeps a static GPU lane. Route memories and judge thresholds are fixed on development episodes before evaluation. The RoboTwin VLA study shares a fixed scene set and the benchmark success criterion across policy types, retaining their native action interfaces and budgets; historical baseline runs are identified separately (Section 4.6 and Appendix C.1).

## 4.2. Routing Beats Each Policy-Generation Baseline

**Routing, not a larger pool, makes the gain.** Table 1 compares REA with each source method evaluated alone on the same episodes. Choosing one method globally on development data selects Agents SDK (94.7%); choosing a method per task at random gives 78.2%. Route memory chooses per task on the same development seeds and reaches 95.9%, +1.2% over the best method (86:51, $p {=} 0.004,$ , paired 95% CI [+0.4, +1.9]%). The comparison is exact on the 37 aligned tasks, where the pool holds only the programs used by the individual baselines: there REA-M reaches 95.3% against 93.7% (54:25, 𝑝=0.001, CI $\left[ + 0 . 6 , + 2 . 5 \right] \% )$ , within 1.0% of the hindsight oracle over the whole pool; on the other 23 tasks it is on par with the best method (96.8 vs. 96.3%). It also costs less: 1,003 steps per success versus 1,343 (−25%), because each task goes to its most reliable policy on development episodes (the SDK program on only 14 of the 60 tasks), and those policies are shorter. **Per program, routing uses less data than policy generation.** Route memory uses 10 development seeds per program (1,790 episodes) and no model tokens, whereas each generation pipeline spent 1,249–1,328 development episodes and 29–89M input tokens on its own library (Appendix A.2). Route memory is as good as an agent at dispatch: REA-A reaches the same 95.9% (26:26 paired) and, as Section 4.3 shows, is slower. **Putting the brain in the control loop does not substitute for policies.** Show-Harness, which asks gpt-6-astra for every move from the images, solves 78 of the 3,000 episodes (2.6%); 2,806 of them end at the 900 s budget, after 34 model calls on average.

## 4.4. REA Improves Policies from Different Methods

## 4.6. VLA and Code Policies Share System 0

**Learned policies run in the same embodied runtime.** We evaluate REA on 50 RoboTwin 2.0 tasks, with one clean and one randomized scene per task (100 episodes). Both use a learned System 1 selector that predicts success from the initial instruction, camera images and robot state, chooses the highest-scoring policy, and retains it for the episode. VLA policies execute native action chunks; the code policy generates and executes a Cartesian gripper command at each decision. This directly instantiates both policy types as System 0 under the common runtime interface (Appendix C.1).

**Combining VLA and code policies improves success.** Table 2 shows 84% success with VLA policies and 86% with the mixed pool, compared with 80% for the MEDex single-VLA baseline. These results provide direct evidence for VLA execution and episode-level dispatch across learned and programmatic policies under the same REA interface. ## 5. Discussion

**Use the brain ahead of time or at policy returns, never inside a running policy.** Dispatching from route memory outperforms each individual policy-generation method and is as accurate as asking an agent at every dispatch, at no online cost (Table 1, Figure 6); consulted in the loop, the brain adds waiting (Figure 4); consulted only when a policy returns, a noisy judge adds success where policies fail silently, at extra time (Table 7, Figure 5). The brain still sets the ceiling (success rates differ by 20–47% across methods), and the router decides how much of it is reached. The gate should be chosen per library on development episodes: the free exception gate suffices when policies rarely fail, the judge gate pays for its calls when they fail silently.

**One interface, different selectors.** The shared Run interface supports both route-memory lookup and learned policy selection. In the RoboTwin 2.0 extension, a learned selector chooses one of seven VLAs or a Python policy from the initial observation and keeps that choice fixed throughout the episode (Section $4 . 6 ,$ Appendix C.1). This study evaluates the shared policy interface and initial selection; recovery-gate effects are evaluated separately on LIBERO-Pro.

## 6. Conclusion

REA separates an embodied system into a System 2 brain, an embodied router and fast System 0 policies under one aligned runtime. On 60 LIBERO-Pro tasks it beats each method that contributes policies to its pool and is the fastest timed pipeline without any online brain call. Its gains come from the router rather than a larger pool: route memory dispatches as well as an online agent at no model cost, and the boundary-triggered judge helps where policies fail silently. The same interfaces carry over to BEHAVIOR-1K, RoboTwin 2.0 and a real Unitree G1, where REA solves the most episodes. The separate 100-episode RoboTwin 2.0 study demonstrates VLA and code policies within the same runtime: REA reaches 84% with VLA policies and 86% with VLA+code, compared with 80% for MEDex, the strongest single VLA baseline. We hope REA becomes a shared platform for developing and comparing embodied brains and fast policies.

## C.1. RoboTwin VLA and Code Policy Integration

**Scenes and execution.** The VLA study uses a fixed set of 100 RoboTwin 2.0 scenes: 50 tasks, each with one clean and one randomized scene, taken from episode 0 of the scene manifest. It preserves each scene’s seed, instruction and initial configuration. These scenes differ from the 200-scene transfer study, which uses episodes 3 and 4. They were used in earlier REA development and serve here as a fixed-scene reevaluation; they are excluded from fitting and selecting the new code head. Both policy types run in the same live simulator and use the official task-success criterion. VLA policies execute their native action chunks and task-specific action limits. The code policy receives four RGB views, robot state, calibration and execution feedback; GPT-6 Astra generates Python that computes one Cartesian move\_gripper target per decision, with at most 40 decisions per episode.

**Selector and training.** A Qwen3.5-4B encoder with LoRA reads the initial instruction, three camera views and robot state. Seven sigmoid heads predict the success of $\pi _ { 0 . 5 } ,$ GigaBrain, Spatial Forcing, X VLA, XWAM, PatchWAM and MEDex. The mixed configuration adds a linear code-policy head, trained with binary cross-entropy on execution success/failure labels while the encoder, LoRA and seven VLA heads remain frozen. The reported checkpoint uses 247 training scenes and 40 development scenes; epoch 4 is selected by mixed-policy success on the development scenes, with code-head loss breaking ties. Later completed calibration scenes are not used to refit this checkpoint. The selector picks the highest predicted success probability at the initial observation and caches that choice for the entire episode; each selected policy continues to react to new observations internally.

**Comparison scope.** Table 2 combines the new VLA configurations with earlier baselines on the same 100 scenes. Codex CLI, OpenAI Agents SDK, the RoboTwin port of ASPIRE, and code-only REA are historical runs. The code-only REA row is the earlier rule-based reflex/deliberate router, not the new Python candidate alone. MEDex is a separate-host rerun with 42 clean and 38 randomized successes. Show-Harness retains its own 100-step budget; the marked historical result uses an adapter later found to accumulate orientation updates incorrectly. The corrected adapter has only a partial run and is not represented by that row. The table reports success rates across these runs; timing comparisons are confined to matched campaigns.

## C.3. Show-Harness Baseline

Show-Harness [43] (commit 5a3713b) is a zero-shot VLM harness: a subgoal planner splits the task into per-arm stages, and a controller prompt asks the model, at every step, for one discrete move per arm (MV\_FWD, MV\_DOWN, . . . , GRASP, RELEASE, DONE) from a front view and the wrist views, with its plugins for proprioception, move memory, grasp recovery and variable step size. We run its code unchanged with gpt-6-astra and supply only the embodiment adapter its authors leave to each lab (views, token directions, begin pose, gripper widths); development episodes set the adapter and never enter the results. **LIBERO-Pro**: single-arm zero-shot mode on the full set (3,000 episodes, the protocol of Table 1), high effort, at most 200 controller decisions, 2 cm fine and 4 cm coarse moves; 78 successes (2.6%), 2,806 episodes end at the 900 s budget (episodes that ended on a provider failure were rerun). **RoboTwin 2.0**: dual-arm zero-shot mode, medium effort, its own 100-step budget; 12 of 200. **BEHAVIOR-1K**: Show-Harness assumes a fixed-base arm at a table, while the R1Pro starts metres from the object, so the approach is scripted before Show-Harness starts (the same search and navigation policies as the other methods, no model call, inside the budget), its GRASP runs the harness’s planned grasp, and moves are inverse-kinematics steps.

## D. Real-Robot Experiments

## D.1. Unitree G1: Walk to and Push a Chair

A Unitree G1 humanoid, secured by a gantry, starts in front of an office chair and receives the instruction take two small steps forward, push the chair, then retract the arms and stand still. Every method uses the same robot, the same model (deepseek-flash, low reasoning) and the same four System 0 policies: walk forward (0.25 m/s for 1 s), the robot’s native two-arm forward push, arm release and stop. ASPIRE writes one program with a single model request (code as policy); Codex + deepseek-flash, run as a separate campaign, writes a program with the Codex CLI; the Agents SDK agent calls the policies as tools (2–3 model requests); REA dispatches each policy at a policy boundary from the head and wrist camera images (4 decisions). Chair contact and displacement are not measured automatically, so Score is the operator’s judgement on site, recorded after each trial.

## D.2. Unitree G1: Latency Check

Our Unitree G1 service, which does not use the router, computes brain decisions ahead of the request: a one-token vision decision (deepseek-v4-flash-vision-exp) as the brain, an in-process fused safety gate (robot state, RealSense depth and Livox lidar vetoes) and locomotion/arm actions as the executor. In pipeline mode a decision loop runs ahead of requests and the service returns the newest decision, 0.04–0.79 s old, which the gate re-checks against a live depth capture at execution (15–40 ms, not part of the request latency). Table 19 reports medians over 5–8 trials on the robot’s onboard computer (Jetson) with live sensors. This measures latency only, not task success.
