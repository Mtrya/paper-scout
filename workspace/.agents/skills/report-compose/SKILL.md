# report-compose

本技能负责写作与交付两个步骤。产出是一份权威研究报告:本地的 `runs/<run-id>/report.docxxml` 源文件和发布的飞书文档。论文文本、代码探针、补丁、MinerU 输出和工作笔记是源材料,不是并行的用户交付物。塑造本技能的失败校准例见 `references/calibration.md`。

起草或发布前加载 `lark-doc`,遵循其 DocxXML 参考;通知前加载 `lark-im`。细则分文件存放:格式与排版 `references/format.md`,审校闸门 `references/review-gates.md`,文风负面清单 `references/anti-ai-zh.md`,图片插入 `references/figure-embedding.md`,交付手工流程 `references/delivery.md`。

## 报告契约

近期论文是研究的种子,不是报告的边界。从新东西出发,沿着最强的线索走:相关论文、代码、产物、诊断、实验、公式、可建造的问题。报告前置的是从论文加外部信号中学到的东西,而不是论文文本的重组。

图示产物是一等公民:公式、代码片段、伪代码、论文插图、结果图、策展图表、产出物、真实表格。它们的目的不是装饰报告,而是比文字更快地展示机制、结果、对比或失败模式。

好的报告洞见密集且可扫读。平实的文字负责定位读者、讲清该看什么、保持逻辑流畅。不要交付一堆只是把论文文本重新排列的密实文字。

报告以中文撰写。

## 写作流水线

写作按一条带质量闸门的流水线推进。主代理负责编排、备料、装配,以及开篇综述与跨主题观察这两处全局写作。深度线程的写作与全部审校则推荐委托给全新上下文的子代理。线程很少的巡航允许主代理直写,简报与闸门不变。

### 备料

写最终稿之前,为每个深度线程写一份写作简报 `drafts/briefs/<thread-id>.md`:

- 图示计划:产物类型、来源、目的、位置(模板见 `references/format.md`)
- 材料路径:线程包、论文缓存、适用记忆条目(术语译法口径)——给原始文件路径,不给二手摘要
- 必读:`references/format.md`、`references/anti-ai-zh.md`、`lark-doc` 的 DocxXML 参考
- 硬约束:读者没读过这篇论文;材料回答不了的问题,回报障碍,不要编

### 线程写作

一个线程一个写手,产物是 DocxXML 片段 `drafts/sections/<thread-id>.docxxml`。写手每完成一个线程,先对照 `references/anti-ai-zh.md` 自检一遍再交回。

### 审校闸门与装配

六道人工闸 + 一道机器闸,定义与执行者见 `references/review-gates.md`。每道只有过/不过;不过则带整改简报原地重写,每线程每闸最多两轮。全部通过后,主代理把线程片段装配为 `runs/<run-id>/report.docxxml`,跑机器门禁(verify_run prepublish),再进入交付。

## 结构

按主题组织,不要平铺成列表。

```xml
<title>Paper Scout 研究报告 - YYYY-MM-DD</title>
开篇综述(2-4 句)
<h1>主题 A</h1>
  小综述(1-3 句)
  短名单表(仅轻量留意的论文;没有则省略)
  <h2>深度线程</h2> + 研究叙事 + 图示产物
  <hr/>
  <h2>深度线程</h2> + 研究叙事 + 图示产物
<h1>主题 B</h1>
  ...
可选:<h1>跨主题观察</h1>
```

### 开篇综述

回答:*这次巡航发现了什么?*点出报告其余部分将使用的主题。如果有一篇论文明显出众,用亮点 callout(示例见 `references/format.md`)。如果这一时期整体平淡,直说。不要硬凑。

### 主题小节

每个真实主题一个 `<h1>`。主题从研究线程中生长出来,不套固定分类法。

- 不要重复论文摘要。一篇轻量留意的论文只出现在一个短名单表里。一个深度线程有一个主要叙事位置,但可以在能讲清线程的地方引用其他论文。
- 深度线程作为 `<h2>` 研究小节放进所属主题;轻量留意的论文作为主题短名单表的行。只有一篇孤文的主题,并入更大的主题或兜底主题;论文池无法聚类时,用单个 `<h1>精选</h1>`。

短名单表四列:**论文**、**核心贡献**、**为什么重要**、**链接**(XML 模板见 `references/format.md`)。贡献与相关性要分开写;主题里每篇论文都被深度线程覆盖时省略表格。单元格塞满段落的表格不算图示产物。

### 深度线程小节

每个深度线程是所属主题下的一个 `<h2>`,用 `<hr/>` 分隔。线程可以围绕一篇论文、一次比较、一个方法问题、一个代码/探针结果,或一个由论文激发的可建造想法。头部格式:

```xml
<h2>论文标题</h2>
<p>作者等(2026)· <a href="url">HF</a> · <a href="url">PDF</a></p>
```

写成流畅的叙事,不要套固定模板。每个深度线程都应讲清:问题是什么、核心机制、调查发现了什么、哪些外部信号支撑、还有什么不确定。排版不是图文交替;载体(`<latex>`、`<pre>`、`<whiteboard>`、`<grid>`、`<callout>`、`<table>`、图片锚点)按叙事功能选择,细则见 `references/format.md`。

### 跨主题观察

只当存在横跨主题的模式时,才加收尾的 `<h1>`:一次趋同、一个空缺、一次转变、一个可复用的方法想法,或一个开放研究问题。没什么可说就跳过。

## 交付

所有 `docs` 命令都带 `--api-version v2`。以 bot 身份创建和更新。创建真实文档之前,确认审校闸门全部通过(含冷读者重建性校验的复检),且机器门禁通过:

```bash
python3 .agents/skills/workspace-manage/scripts/verify_run.py runs/<run-id> --mode prepublish
```

### 飞书交付(需要 lark-cli)

PATH 上有 `lark-cli`(或可通过 `npx --yes @larksuite/cli` 拉起)时走完整飞书流程;没有则跳到仅本地兜底。首选方式是本技能的推送脚本,它封装了分段、插图与验证的全部细节:

```bash
python3 .agents/skills/report-compose/scripts/push_report.py <run-id> \
  --user-id <ou_xxx>   # 不给 --user-id 则只建文档不通知;--dry-run 只分段并打印计划
```

完整选项、手工等价流程与故障排查见 `references/delivery.md`。bot 拥有产出的文档;没有 `--parent-token`,也没有配置文件夹/知识库目的地——不要自己加。内容里的 `<title>` 元素设置文档标题。

然后加载 `lark-im`,给用户发一条包含文档 `url` 的私信。用 `--text`(不是 `--markdown` 或 `--content`),这样飞书会把文档 URL 自动展开成富预览卡片:

```bash
lark-cli im +messages-send --as bot --user-id <ou_xxx> \
  --text "https://<tenant>.feishu.cn/docx/<doc_id>"
```

只有当这条私信发出并确认后,一次巡航才算完成。如果收件人解析或发送失败,停下并报告。私信确认之后:

1. 确保已交付的 DocxXML 源文件保存在 `runs/<run-id>/report.docxxml`。
2. 保存文档 `url`,交给 `workspace-manage` 记入 `runs/INDEX.md`。

### 仅本地兜底(无 lark-cli)

当 `lark-cli` 未安装时,优雅地跳过飞书交付,不要视为错误:确保源文件保存在 `runs/<run-id>/report.docxxml`,用工作区绝对路径告诉用户报告位置,照常进入 `workspace-manage` 收尾流程,并在 `runs/INDEX.md` 中用本地路径代替飞书 URL。

## 不要做什么

- 不要省略或重复 `<title>`。
- 不要用 `overwrite` 在巡航中途修报告。用 `append`,或 `lark-doc` 中文档化的块级编辑命令。
- 不要在 `<callout>` 里放裸文本、表格或代码块。
- 不要写"取得了 SOTA"。写数字、基准和比较对象。
- 不要整份报告都用平铺的要点列表。
- 不要给每个深度线程盖上同样的五个小标题。
- 不要把深度线程又复制成短名单的一行。
- 不要把整个论文池做成一张巨大的短名单表。
- 不要硬编码主题列表。
- 不要交付只是复述摘要的深度线程。
- 不要在交付的文档里留下可见的临时媒体锚点。
- 不要跳过私信就认为交付完成(除非 lark-cli 不可用且你在走仅本地兜底)。
- 通知 URL 不要用 `--markdown` 或 `post` 内容;那会渲染成朴素的蓝色链接,而不是飞书文档卡片。
- 不要发明收件人解析规则;遵循 `lark-im`。

写作:

- [ ] 已加载 `lark-doc`;每个深度线程有写作简报(图示计划、材料路径、必读清单、硬约束)
- [ ] `<title>` 存在且不重复;开篇综述点出了研究主题
- [ ] 短名单表按主题组织且只含轻量留意的论文
- [ ] 排版载体按叙事功能选择;同类多张相关小图用 `<grid>` 横排

审校:

- [ ] 六道人工闸全部通过(含冷读者重建性复检),整改简报闭环

交付:

- [ ] 通知前已加载 `lark-im`
- [ ] 运行清单已完成;verify_run prepublish 通过
- [ ] 本地媒体锚点已插入、解析、删除并验证

- [ ] 创建/更新命令在真实写入前做过 dry-run
