# report-compose

本技能负责写作与交付两个步骤。产出是一份权威研究报告:本地的 `runs/<run-id>/report.docxxml` 源文件和发布的飞书文档。论文文本、代码探针、补丁、MinerU 输出和工作笔记是源材料,不是并行的用户交付物。塑造本技能的失败校准例见 `references/calibration.md`。

起草或发布前加载 `lark-doc`,遵循其 DocxXML 参考;通知前加载 `lark-im`。细则分文件存放:格式与排版 `references/format.md`,审校流程 `references/review-gates.md`,写作避坑 `references/anti-ai-zh.md`,图片插入 `references/figure-embedding.md`,交付手工流程 `references/delivery.md`。

## 报告契约

近期论文是研究的种子,不是报告的边界。从新东西出发,沿着最强的线索走:相关论文、代码、产物、诊断、实验、公式、可建造的问题。报告前置的是从论文加外部信号中学到的东西,而不是论文文本的重组。

图景先于符号:每个深度线程都以一个具体的问题、失败案例或反直觉现象开场,再引入必要的术语、前作与公式。不按论文章节顺序逐段转述,也不把背景与基线一次性堆在机制前面。

图示产物是一等公民:公式、代码片段、伪代码、论文插图、结果图、策展图表、产出物、真实表格。它们的目的不是装饰报告,而是比文字更快地展示机制、结果、对比或失败模式。

好的报告先让读者看懂这件事从哪来、为什么非解不可,再把改变判断的洞见摆在正确的位置上。平实的文字负责定位读者、讲清该看什么、保持逻辑流畅。不要交付一堆只是把论文文本重新排列的密实文字。

语言质地以**费曼物理学讲义**式的物理直觉与对话感为范:句子完整、术语确切、节奏从容,像在黑板前把机制从头算穿;可读性来自清晰的逻辑引导,而不是口语化措辞或时髦词。

报告以中文撰写。

## 写作流水线

写作按一条带质量闸门的流水线推进。主代理保有研究主线、核心证据判断与全文提纲,负责编排、备料、装配与最终验收,始终承担理解与综合。深度线程与全局写作、编辑和冷读优先委托给全新上下文的子代理,主代理不因线程较少就自动直写。

写作、结构编排与冷读必须显式选择文字能力与结构判断俱佳的模型,冷读不能以辞采代替结构判断;编辑按编辑能力选择,执行类工作选择足以完成任务的低成本模型。代理类型只决定工具权限,不代表文字或审读能力。不得无说明地继承默认模型(诱惑:省去一次选择看似无碍,实际上同时放弃了表达质量与成本控制)。环境确实不支持模型选择时才回退并记录。文字能力不能替代证据核对,事实正确性仍由第一关(主线与事实)负责。

### 主线与全文提纲

写最终稿之前,重读当轮 prompt 与用户点名主题,不从调查目录、执行顺序或已有草稿反推主线。主代理写全文提纲 `drafts/report-outline.md`:

- 当轮主线与交付目标,以及各线程在其中的职责;若单轮聚焦 1–2 个线程,问题边界要格外窄而实
- 线程之间的前提依赖与顺序理由,不替线程设计每一段
- 每个线程的衔接契约:读到这里时读者已经知道什么、本线程必须建立什么、哪些内容交给后文
- 每个线程的开场锚点:用哪个具体失败、玩具案例或反直觉现象把读者拉进来

核心问题仍在调查时可以维护提纲,但不得锁定候选稿结构;新结果改变论证时先改提纲,再改正文。全文写作者或装配者才接收全文提纲与全部线程提纲。

### 线程提纲与备料

为每个深度线程写一份写作简报 `drafts/briefs/<thread-id>.md`,由主代理或负责该线程的调查代理拥有:

- **白板底稿(核心动机与主线)**:动笔前必须先用人话写清三点——
  1. **矛盾是什么**:前人或基线在什么具体场景下会崩?继承的前作到底卡在哪里?
  2. **本作的真正切口**:作者究竟动了哪处最小关键改动解决了这个矛盾?
  3. **判定与实证边界**:这一刀真的管用吗?代价是什么?我们的调查、探针或实验看到了什么局限或新判断?
- **线程叙事提纲**:围绕上述主线展开段落——从具体失败或矛盾开场,引入理解问题所必需的最小前作与机制,再呈现关键证据与锐利判定。
- **锚点案例**:开场用的具体失败、玩具情形或反直觉结果,以及它为什么能代表核心矛盾。
- **衔接契约**:只取全文提纲中与本线程有关的输入、输出与职责边界。
- **图示计划**:产物类型、来源、目的、位置(模板见 `references/format.md`)。
- **材料路径**:线程包、本作与承重前作的论文缓存、适用记忆条目(术语译法口径)——给原始文件路径,不给二手摘要。
- **必读**:`references/format.md`、`references/anti-ai-zh.md`、`lark-doc` 的 DocxXML 参考。
- **硬约束**:读者没读过这篇论文;先理顺动机、前因后果与核心矛盾再讲机制;材料回答不了的问题,回报障碍,不要编;允许有立场的锐利判断,但事实与推测边界分明;留出自然的逻辑过渡与呼吸感,不把句子硬焊在一起;实验细节只在它支撑的判断旁入场,复现专有细节留在证据包;正文只解读读者该带走什么,原始矩阵交给表格。

线程写手只接收本线程提纲、衔接契约与所需材料,不接收整份全文提纲。它可以直接反驳本线程提纲;涉及全文顺序或其他线程的异议交回主代理,不让局部写手越权重排全篇。

### 提纲反驳与线程写作

先让写手审查线程提纲与衔接契约,不直接成文。提纲异议解决后,再续派同一写手写作 DocxXML 片段 `drafts/sections/<thread-id>.docxxml`;小型巡航可以由主代理同时拥有两层提纲,但不省略提纲审查。写手每完成一个线程,先对照 `references/anti-ai-zh.md` 自检一遍再交回。

### 审校与装配

交付前过两道人工关 + 一道机器门禁,定义见 `references/review-gates.md`。写前定好每个线程的"前因后果/动机"主线,写后核对全文事实与线程包证据一致(允许有立场的锐利判断,但必须标明实证与推断的边界),再由独立冷读者按原文顺序小步首读——回答"哪里卡住读不懂""哪里读着像机器、不爽",以及读完后能否复述这条线程的核心判断。结构性修订后由新的冷读者重新顺序首读,最后跑机器门禁(verify_run prepublish)并进入交付。

## 结构

按主题组织,不要平铺成列表。

```xml
<title>Paper Scout 研究报告 - YYYY-MM-DD</title>
开篇综述(2-4 句)
<h1>主题 A</h1>
  小综述(1-3 句)
  短名单表(仅轻量留意的论文;没有则省略)
  <h2>深度线程</h2> + 研究叙事 + 图示产物
  <hr/>
  <h2>深度线程</h2> + 研究叙事 + 图示产物
<h1>主题 B</h1>
  ...
可选:<h1>跨主题观察</h1>
```

### 开篇综述

回答:*这次巡航发现了什么?*点出报告其余部分将使用的主题。如果有一篇论文明显出众,用亮点 callout(示例见 `references/format.md`)。如果这一时期整体平淡,直说。不要硬凑。

### 主题小节

每个真实主题一个 `<h1>`。主题从研究线程中生长出来,不套固定分类法。

- 不要重复论文摘要。一篇轻量留意的论文只出现在一个短名单表里。一个深度线程有一个主要叙事位置,但可以在能讲清线程的地方引用其他论文。
- 深度线程作为 `<h2>` 研究小节放进所属主题;轻量留意的论文作为主题短名单表的行。只有一篇孤文的主题,并入更大的主题或兜底主题;论文池无法聚类时,用单个 `<h1>精选</h1>`。

短名单表四列:**论文**、**核心贡献**、**为什么重要**、**链接**(XML 模板见 `references/format.md`)。贡献与相关性要分开写;主题里每篇论文都被深度线程覆盖时省略表格。单元格塞满段落的表格不算图示产物。

### 深度线程小节

每个深度线程是所属主题下的一个 `<h2>`,用 `<hr/>` 分隔。线程可以围绕一篇论文、一次比较、一个方法问题、一个代码/探针结果,或一个由论文激发的可建造想法。头部格式:

```xml
<h2>论文标题</h2>
<p>作者等(2026)· <a href="url">HF</a> · <a href="url">PDF</a></p>
```

写成流畅的叙事,不要套固定模板,也不要按论文章节顺序逐段转述。每个深度线程都把前因后果理顺:先用具体的问题、失败案例或反直觉现象把读者拉进来,再只引入解开它所必需的前作与概念,把机制从剥离后的玩具或直觉模型讲到真实系统,然后呈现在改变判断处入场的证据,最后给出有立场的判断与开放边界。排版载体(`<latex>`、`<pre>`、`<whiteboard>`、`<grid>`、`<callout>`、`<table>`、图片锚点)按叙事功能选择,细则见 `references/format.md`。表格与图表承载原始矩阵,正文只做解读,不逐行复述单元格;允许自然的逻辑过渡与呼吸感,不要用分号和破折号把事实硬焊在一起。

当某篇优秀论文或深度博客长文值得推荐通读时,不要强行做粗暴压缩。以独立推荐小节或亮点 `<callout>` 呈现:给出简短导读,说明作者解决的核心问题、行文或推导的独到之处、以及读者该带着什么问题去读原文,并附上原文直达链接。

### 跨主题观察

只当存在横跨主题的模式时,才加收尾的 `<h1>`:一次趋同、一个空缺、一次转变、一个可复用的方法想法,或一个开放研究问题。没什么可说就跳过。

## 交付

所有 `docs` 命令都带 `--api-version v2`。以 bot 身份创建和更新。创建真实文档之前,确认两关审校通过,且机器门禁通过:

```bash
python3 .agents/skills/workspace-manage/scripts/verify_run.py runs/<run-id> --mode prepublish
```

### 飞书交付(需要 lark-cli)

PATH 上有 `lark-cli`(或可通过 `npx --yes @larksuite/cli` 拉起)时走完整飞书流程;没有则跳到仅本地兜底。首选方式是本技能的推送脚本,它封装了分段、插图与验证的全部细节:

```bash
python3 .agents/skills/report-compose/scripts/push_report.py <run-id> \
  --user-id <ou_xxx>   # 不给 --user-id 则只建文档不通知;--dry-run 只分段并打印计划
```

完整选项、手工等价流程与故障排查见 `references/delivery.md`。bot 拥有产出的文档;没有 `--parent-token`,也没有配置文件夹/知识库目的地——不要自己加。内容里的 `<title>` 元素设置文档标题。

然后加载 `lark-im`,给用户发一条包含文档 `url` 的私信。用 `--text`(不是 `--markdown` 或 `--content`),这样飞书会把文档 URL 自动展开成富预览卡片:

```bash
lark-cli im +messages-send --as bot --user-id <ou_xxx> \
  --text "https://<tenant>.feishu.cn/docx/<doc_id>"
```

只有当这条私信发出并确认后,一次巡航才算完成。如果收件人解析或发送失败,停下并报告。私信确认之后:

1. 确保已交付的 DocxXML 源文件保存在 `runs/<run-id>/report.docxxml`。
2. 保存文档 `url`,交给 `workspace-manage` 记入 `runs/INDEX.md`。

### 仅本地兜底(无 lark-cli)

当 `lark-cli` 未安装时,优雅地跳过飞书交付,不要视为错误:确保源文件保存在 `runs/<run-id>/report.docxxml`,用工作区绝对路径告诉用户报告位置,照常进入 `workspace-manage` 收尾流程,并在 `runs/INDEX.md` 中用本地路径代替飞书 URL。

## 不要做什么

- 不要省略或重复 `<title>`。
- 不要用 `overwrite` 在巡航中途修报告。用 `append`,或 `lark-doc` 中文档化的块级编辑命令。
- 不要在 `<callout>` 里放裸文本、表格或代码块。
- 不要写"取得了 SOTA"。写数字、基准和比较对象。
- 不要整份报告都用平铺的要点列表。
- 不要给每个深度线程盖上同样的五个小标题。
- 不要把深度线程又复制成短名单的一行。
- 不要把整个论文池做成一张巨大的短名单表。
- 不要硬编码主题列表。
- 不要交付只是复述摘要的深度线程。
- 不要在交付的文档里留下可见的临时媒体锚点。
- 不要跳过私信就认为交付完成(除非 lark-cli 不可用且你在走仅本地兜底)。
- 通知 URL 不要用 `--markdown` 或 `post` 内容;那会渲染成朴素的蓝色链接,而不是飞书文档卡片。
- 不要发明收件人解析规则;遵循 `lark-im`。

## 验收

写作与交付的逐项验收统一遵循 `workspace-manage` 的清单模板（落盘于 `runs/<run-id>/checklist.md`），不在本技能内重复维护第二份清单。

发布前的核心检查点：
- **两关审校**：第一关主线与事实（理顺动机、核对证据不编造）及第二关独立冷读者（只看正文、按顺序首读、能复述核心判断）已全部通过。
- **机器硬伤门禁**：`python3 .agents/skills/workspace-manage/scripts/verify_run.py runs/<run-id> --mode prepublish` 零错误。
- **飞书闭环**：文档创建、本地图片锚点解析与插入、用户私信通知确认，飞书 URL 记入 `runs/INDEX.md`。
