# paper-deep-dive

以一个好奇的研究者的角色进入作品:理解核心想法,把它变具体,通过追踪、运行、复现、推导、比较或做一个小探针来吃透一篇论文或研究文章。塑造本技能的失败校准例见 `references/calibration.md`。

工作区布局、线程包与校验器规则,遵循 `workspace-manage`。

## 线程包

一个线程是 `runs/<run-id>/<thread-id>/` 下的持久调查单元。它可以是一篇论文或研究文章、一次跨作品比较、一个方法问题、一条代码路径,或一个由作品激发的可建造想法。

使用以下形态之一:

- `README.md`(当线程的证据本身就是精读、源码追踪、跨论文三角验证或数学推导时;`lite` 流里这是常态,`full` 流里只用于确实不需要自写脚本的线程——但须写清可独立复核的逐行依据与推导步骤)
- `README.md` + `code/`
- `README.md` + `patches/`
- `README.md` + `code/` + `patches/`
- `BLOCKER.md`

`README.md` 说明尝试了什么、保留了什么证据、如何重跑(如适用),以及结果对报告意味着什么。`BLOCKER.md` 用于极少数情况:没有任何有意义的外部信号可以保留;它应把障碍讲得足够清楚,让报告可以诚实地面对它。

线程包要写到自足:一个没有你任何上下文的人(或写作阶段的写手子代理)仅凭包内材料,就能重建问题、方法、证据与发现。凡是只存在于你脑子里的指代、配置与中间结论,不写进包里就等于没做——把隐性的东西想清楚再落盘,这件事本身就是调查的一部分。

## 获取与阅读

1. 通过 `paper-source` 获取论文(`hf papers read` 或 arXiv PDF + MinerU)或科学空间文章(RSS 发现,镜像 Markdown 或原页精读),把 Markdown 存到 `papers/<area>/<slug>-<id>.md`。
2. 通读全文,包括附录;系列文章先读理解当前篇所必需的前作,不扩张成全系列通读。
3. 识别作品的问题、声称的贡献、核心机制、关键证据,以及对本次巡航重要的问题。

## 把方法变具体

把方法讲到足够密,密到你可以大致复现或修改它:

- 输入与输出
- 主要阶段及其连接方式
- 不直观的设计选择
- 承载方法的公式、损失、指标、提示词、数据变换或控制回路
- 论文实验对当前研究问题提供了什么证据;哪个具体替代解释一旦成立,就会改变结论

需要时补上被跳过的推导;注明你是在补充而不是引用。

## 寻找外部信号

洞见来自论文加外部信号。让调查迭代起来:提出一个活的问题,采取最强的可行建设性动作,检视结果,重新解读线程,决定下一个问题。按当轮运行流选择投入重点:

- **`full` 流**:优先推进真实实验与可运行验证——端到端追踪官方代码、跑通真实权重/数据路径、做消融或指标核验、必要时按 `remote-compute` 上远程 GPU;与承重前作精读并重。
- **`lite` 流**:以**文本与代码证据**为主轴——通读全文与承重前作、跨论文三角验证、逐行追踪官方仓库源码与配置、做独立数学推导或反例构造,辅以直观、轻量的本地或 Colab 探针/绘图。不要求多阶段重训练或大规模 GPU 复现;不要为了凑 `code/` 而写毫无信息量的玩具脚本,高质量的源码审计与推导记录直接写进 `README.md`。

优先选择这类动作:

- 端到端追踪官方代码
- 在实现里跑通一条小路径
- 检查配置、预处理、数据样本、检查点或评测脚本
- 对某个组件做性能剖析或探针
- 在玩具案例上复现核心机制
- 推导一个缺失的细节
- 与相关实现或论文比较
- 跑一个小消融、指标核验或基准子集

当官方代码或产物存在时,它们是最强的信号,要用起来。在 `code/` 下克隆或工作,使用显式的命令工作目录和直接的环境二进制路径,而不是依赖持久的 `cd` 或虚拟环境激活。

如果官方产物不完整或不可用,不要停在这个观察上。以谦逊的规模复现核心想法,检查相关实现,或读能检验新东西的相关论文。如果这些动作在巡航资源内都无意义,保留 `BLOCKER.md`。

相关论文直接提供外部信号:它们交代概念、方法与问题表示的来路,比较不同设计的假设与效果,为理解本作、设计后续实验和形成跨作品判断提供地基。

主代理保有研究问题与核心证据判断。可独立交付的代码追踪、相关论文检查、依赖调试与日志整理交给能力和成本相称的子代理,环境支持时明确选择与任务相称的模型;一次性小探针不必为委派而委派。子代理交回证据与判断依据,主代理始终承担理解与综合。

## 地基与邻里

线程启动时先列地基清单:这篇论文依赖哪些前置概念、分别来自哪几篇论文;同期池内有没有同问题或反对立场的论文。承重地基(1–3 篇)要真读,不是只读摘要——报告的读者默认只有基础概念,preliminaries 讲不清,后面的一切都悬空。论文题名、摘要或正文点名的直接前作(它明确继承或改进的方法)自动进入承重地基,不可豁免;这类前作在线程启动时就要识别并定向精读,不是写作阶段再补。只读本作的 Related Work 转述不算读过前作。

相关论文与实验是两类并列的外部信号。地基阅读本身就是调查动作,既为读者建立教学地基,也可能直接改变研究判断;不得用代码与实验挤掉它(诱惑:可运行的实验更像研究动作,文献则容易被当成写作前的背景补课)。按当前问题的预期洞见分配文献与实验的投入,实验不天然优先;定向精读不扩张成领域普查。

当能让发现更锐利时,把线程放进承重邻居的坐标里:关键基线、最接近的竞争方法、方法前身,或相关代码库。目标是三角验证,不是抄谱系。

## 好奇心清单

收尾每个线程之前,列出"如果我是这个领域的研究者,接下来会好奇什么"——不限于论文自己提出的悬念:数据形态、范式边界、未被检验的假设都值得问。清单上能追的问题转成研究动作追下去,追不了的进报告的未来方向或日期记忆。研究动作不只从论文的悬念里长出来,也从这张清单里长出来。

## 提炼报告材料

实验分析遵循 `experiment-lifecycle` 第 4 节:围绕预设问题阅读完整轨迹与内部指标,明确假设是否成立、学到了什么、下一步改变哪个判断。

捕捉能让报告洞见密集且可扫读的材料:

- 研究问题,以及这次巡航学到了什么
- 背景与直接前作的原文证据:前人如何建模问题、本作继承了什么、改变了什么,不能只凭本作 Related Work 二手压缩
- 用文字、公式、伪代码或紧凑代码片段表达的核心机制
- 能讲清故事的论文插图、结果表格、实验图或产出物
- 影响报告能负责任地声称什么的局限、障碍与不确定性
- 研究结论:这个线程教会本次巡航什么、报告因此应该声称什么、下一步最值得检验的猜想

## 保存证据

报告交付前,把持久工作从 `code/` 晋升到线程包:

- 代理写的探针、复现、封装、指标核验、合成实验或紧凑可运行示例,放入 `runs/<run-id>/<thread-id>/code/`
- 针对官方代码的补丁,放入 `runs/<run-id>/<thread-id>/patches/`
- 面向报告的媒体与小型结果产物,放入 `runs/<run-id>/assets/`
- 原始克隆仓库、虚拟环境、大日志、缓存与暂存保持被忽略,在持久证据晋升后清理

按 `workspace-manage` 的指引运行工作区校验器;如果失败,修正运行包,而不是削弱证据。

## 不要做什么

- 不要把转述当作调查交付。
- 不要把摘要当作事实。
- 有可用代码时,不要跳过代码检查。
- 不要停在"没有代码";尝试重构、相关实现或相关论文三角验证。
- 不要作秀式复现。资源的投入要由预期洞见来辩护。
- 不要无目的地罗列相关工作;有教学或洞见目的的精选地基是义务,不是文献综述。
- 不要跳过好奇心清单就收线程;清单可以短,但不能没有。
- 不要停在记录代码与论文的不一致;解释这个差距在相关工作和更大的研究问题中意味着什么。
